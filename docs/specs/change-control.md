# 变更、提交与PR

规范版本：1.0.3。本次建立的工程约定，目的为让下一位开发者和Agent读取同一依据。

## 一次改动的最小闭环

1. 定位注册表里的岗位、页面和方法版本，再读取相应实现。已有要求照做；新增产品取舍另列待确认，不靠实现悄悄决定。
2. 在 `codex/<任务>` 分支做范围清楚的改动。并行开发使用独立worktree；同一工作目录切分支不能隔离写入。发现其他任务的未提交文件时保留，不覆盖、不暂存到本任务。规范变化和实现变化同一PR说明；仅文案排版修正也要更新对应文档补丁版本。
3. 对变更文件更新注册版本与 CHANGELOG，再执行 `python3 scripts/check-specs.py --freeze`。普通检查用 `python3 scripts/check-specs.py`，不要用刷新锁掩盖未读差异。
4. 做与改动相称的实际验证。页面给前后图和交互证据；业务给输入／产物／原生回执；文档整理核引用、版本和原件。不同验证各说明范围。
5. 提交可审查差异，PR列问题、结果、规范影响、证据和未完成项。评审通过后再合并；GitHub分支保护需远程仓库建立后另行配置，当前没有假称已生效。

版本使用 `主.次.补丁`：不兼容职责／合同改主版本，兼容增加改次版本，表述、路径和纠错改补丁。Skill的原生版本与本规范登记版本分别保存，不伪造上游发版。策略不因治理版本号恢复复杂Skill。

`--base <提交>` 检查会比较基线锁：内容变化而登记版本未变化时失败。退役条目保留历史身份及替代入口，不直接消失。规范与实现不一致时记录差异，不宣布完成。

## 初次纳管

本目录开始时没有提交。第一份规范基线提交只能从当前时刻开始回退，无法补出过去的逐步历史。没有基分支时也没有可真实评审的既往PR。

先建立选定的规范基线提交，再在后续分支提交源码纳管或功能改动、发真实PR。首次规范提交不等于全项目源码已被保护。现有临时源、数据库、失败记录、客户PDF和生成图保持原位；不得 `git add .` 把它们一起上传。源码纳管范围见[清单](repository-scope.md)。

## 回退

已合并改动用新的 revert 提交及PR撤回，保留决定与证据。临时查看旧提交使用独立 worktree／检出目录，不覆盖当前未提交成果；不通过强制回退或清理删除用户文件。业务数据库与产物版本按原生恢复协议处理，Git回退不替代业务回滚。

## Git与远程的实际边界

2026-11-11首次规范核查已读到本地提交，当时分支为 `codex/spec-baseline-20261111`，origin配置为 `git@github.com:marctubud-pixel/pitch-agent.git`。本地配置只证明已有目的地址，不证明推送、仓库可见性、PR、CI或分支保护已核验；规范整理时未对外写入。用户本轮已明确授权工程源码纳管与常规推送，实际结果以远程引用及发布回执为准。客户资料、原始PDF、业务库、凭据和大型生成产物不纳入首批上传。

规范实际依赖的评审协议和Skill附录也纳入注册或其方法文件组；仅锁入口文件不足以约束执行。干净检出需包含AGENTS的必读相对路径。

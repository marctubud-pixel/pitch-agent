# 提案工作台前端开发指南

本文说明如何在现有本地工作台上开发独立的产品化前端。它描述当前可用能力与约束，不代表完整提案自动化已经实现。

## 项目现状

工作台使用 Node.js 本地 HTTP 服务和 SQLite 保存项目、版本、任务、成果、审查与交接记录。当前页面位于 `tools/workbench/ui.html`，服务端位于 `tools/workbench/server.mjs`。默认端口为 4181。端口 4180 的 `tools/auto-layout` 是独立排版工具，不属于工作台流程。

现有页面已支持项目创建、任务卡确认和修订、模式与人工节点设置、来源录入、文字阶段任务提交、成果和历史查看、独立摘录核验、充分性审查、负责人交接、调研到策略继续、图片登记与观察任务，以及失败结果本地恢复。页面是流程验证界面，尚未形成完整的产品视觉系统。

当前后端仍有明确缺口：自动网页搜索和抓取、图片生成、创意评分与对抗评审、后续阶段继续执行、完整排版交付尚未打通。图片观察已接入上传与独立观察，但观察结果与调研引用、核验、充分性及交接的完整证据链还未完成。不得在界面中把尚未接通的步骤显示为已完成或可放行。

## 目标

构建清晰、可追溯的提案工作台，让用户能看懂项目处于哪个阶段、当前成果依据什么、有哪些阻断项，以及下一步能执行什么操作。先改进现有工作流的呈现和操作体验；新增后端能力必须依据服务端实际接口，不能用前端状态模拟业务事实。

## 建议的信息架构

1. **项目列表与新建**：项目名、Brief 摘要、当前版本、更新时间或进度提示。
2. **项目概览**：Brief 与任务卡状态、当前模式、人工节点、阶段进度、最近活动和待处理事项。
3. **研究工作区**：研究成果、来源、引用摘录、论断、核验报告、充分性报告与未解决问题。
4. **阶段交接**：研究负责人和策略负责人签收状态、允许用途、禁止推论、放行阻断原因和继续执行入口。
5. **执行记录**：任务状态、执行阶段、模型调用回执、失败原因、恢复入口及完整历史版本。
6. **资料与观察**：上传图片、图片元数据、观察结果与其审核状态。要清楚标注观察不能认证来源或消费者偏好。

将“当前可执行操作”放在对应阶段内容旁边，并根据服务端 capability 和项目状态禁用不可用操作。展示阻断原因，不要只显示灰色按钮。

## API 与数据边界

以 `tools/workbench/server.mjs` 的路由和 `tools/workbench/README.md` 为准。当前 UI 与服务同源，通过 JSON 请求访问 API。主要接口如下：

| 用途 | 方法与路径 | 说明 |
|---|---|---|
| 获取能力 | `GET /api/capabilities` | 返回阶段、工具可用性与限制原因。能力可能随模型配置变化。 |
| 列出项目 | `GET /api/projects` | 返回项目标识、名称和当前版本号。 |
| 创建项目 | `POST /api/projects` | 创建项目和初始任务卡；需要 `commandId`、`name`、`brief`，策略字段可使用服务端默认值。 |
| 读取项目 | `GET /api/projects/:id` | 返回当前项目状态；可用 `?revision=N` 读取历史版本。 |
| 记录用户决策 | `POST /api/projects/:id/commands` | 仅接受服务端允许的人工命令。提交 `expectedRevision` 和唯一 `commandId`。 |
| 提交文字任务 | `POST /api/projects/:id/jobs` | 当前仅支持 `research`、`strategy`、`copy` 阶段；调研可提交 `sourceRecords`。 |
| 读取成果正文 | `GET /api/projects/:id/artifacts/:artifactId/content` | 服务端校验登记路径与哈希后返回成果内容。 |
| 资料核验、充分性、交接、继续 | `POST /api/projects/:id/verifications`、`readiness`、`handoffs`、`continuations` | 各接口字段见服务端实现与 README。它们会创建实际任务或命令，不是纯 UI 状态更新。 |
| 图片与观察 | `POST /api/projects/:id/images`、`GET /api/projects/:id/images/:imageId`、`POST /api/projects/:id/observations` | 上传有大小限制；只传字节，不传本机文件路径。 |
| 本地恢复 | `POST /api/projects/:id/reconciliations` | 只对符合条件的已保存成果重新校验，不重复调用模型。 |

大多数修改请求都需要 `commandId` 和 `expectedRevision`。版本冲突时重新读取项目，再由用户确认后重提；不能静默覆盖。重复提交必须复用同一命令 ID 和相同请求体。用户发起新操作时创建新的 ID。

API 响应会随项目领域模型演进。实现前检查最新 `server.mjs`、`project.mjs` 和 README，不要只依赖本指南中的字段概述。前端不得自行构造模型身份、审查评分、事实核验结果、签收结果、放行记录或任务完成状态。所有业务状态以服务端返回为准。

## 实现约定

- 优先在 `tools/workbench/` 内增加前端模块，并保留本地服务同源部署方式，除非项目负责人明确决定更换技术栈或部署形态。
- 不要改动 `tools/auto-layout/` 的独立入口或端口来实现工作台页面。
- 每个页面状态都能对应到服务端项目数据、能力响应或明确的本地临时 UI 状态。临时状态不可伪装成已保存状态。
- 对排队、运行中、待核对、失败、成功但未放行、过时版本分别设计状态呈现。任务提交成功不等于成果通过审核。
- 保留历史版本只读访问。对未保存输入离开页面时提示用户。
- 图片、原始回执和引用使用服务端 ID；不要在浏览器拼接本地路径或相信客户端提供的哈希。
- 错误消息要显示可采取的操作，例如刷新后核对版本冲突、查看任务回执或使用符合条件的本地恢复入口。
- 保持键盘可操作、语义化控件、足够的文字对比度和窄屏可读性。危险或不可逆业务动作需要清楚说明对象和影响。

## 开发顺序

1. 阅读本指南、`tools/workbench/README.md`、`tools/workbench/ui.html`、`tools/workbench/server.mjs` 和 `多线调研工作台_开发说明_v0.3.md`。
2. 盘点现有页面和响应字段，写出前端页面结构与组件边界，再开始实现。
3. 先完成项目列表、项目概览、研究成果与阻断项，再整理任务执行和交接交互。
4. 接入实际 API；对未支持的能力显示“尚未接入”及当前原因，不创建虚假按钮流程。
5. 运行现有服务，在浏览器中验证创建项目、读取历史、版本冲突和主要操作的真实状态呈现。不要只凭静态截图判断接口接入成功。
6. 交付时列出改动文件、实际验证步骤、仍依赖后端补齐的能力。

## 关键文件

- `tools/workbench/ui.html`：现有工作台页面。
- `tools/workbench/server.mjs`：HTTP 路由和请求校验。
- `tools/workbench/project.mjs`：领域状态与命令规则。
- `tools/workbench/store.mjs`：SQLite 持久化。
- `tools/workbench/README.md`：启动方式、当前能力和接口细节。
- `多线调研工作台_开发说明_v0.3.md`：产品流程、门禁与交付约定。

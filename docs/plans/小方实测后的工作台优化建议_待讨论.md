# 小方实测后的工作台优化建议

日期为2026年11月3日。状态为待讨论，安排在当前开发节点完成后评估。本文件保存竞品实测带来的改进建议，不作为新增开发规格、任务排期或运行授权。

## 对主流程和功能板块的影响

这些建议可以在现有工作台内分步落实，无需重划主流程或功能板块。主要工作是接通和验收已有能力，改善阶段内部的质量检查、任务调度和结果展示。部分建议会影响内部顺序、调用成本或交互，需要另行讨论，不能承诺所有实现都没有影响。

现有界面的八阶段继续作为比较基线：任务与Brief、调研、策略、文案与主题、视觉开发、内容审查、排版、终审与交付。来源核验、研究充分性、评审、交接和版本检查仍位于相应阶段内部，不为这次优化另设主阶段。

功能板块继续沿用总览、提案工作区、资料库、过程与历史、交付，以及旁侧的WorkBot。优化落在对应板块内部。当前前端的真实接入、演示内容与未实现能力仍分别标识。

以下产品约定继续生效：

- KV与海报、包装设计仍为既有任务类型。各自交付内容不因小方样本而缩减，也不把所有任务改成营销全案。
- 任务驱动的调研、三圈收拢、主题先于视觉、参考与草图及成稿的分阶段评审、内容先于正式排版的依赖关系继续保留。
- 自动模式、辅助模式以及各项目的人工决定，均按当前有效协议和最新用户授权执行。本文件不新增逐阶段确认，不恢复已取消的逐张参考人工确认。
- 现行主题方向与三案差异要求继续执行。小方测试中使用的冻结Brief与历史方向分类不反向替换工作台当前规则。
- 独立评审、已确认的创意权限、版本留存、事实核验、来源追溯、预算和异常恢复要求继续生效。偏好采用不使事实变成已核验，不以完成状态或平均分掩盖有效阻断。
- 客户提案与内部评分、过程记录分开。网页、PDF和当前产品目标中的可编辑PPTX交付边界继续依照现有依据，不因小方只完成三张图而降低。

界面八阶段与业务规则中的细分审校、交接步骤属于不同层级，不能据此误判现有主流程发生冲突。遇到历史暂停状态、旧分类或旧确认规则，按最新用户指令、有效运行协议和权威检查点解释。

依据见[前端工作区及能力边界](../../apps/proposal-workbench/README.md)、[现行工作流](../workflows/提案工作流_现行规则.md)、[任务范围与三级协作](../workflows/任务范围与三级协作.md)和[开发说明](../../多线调研工作台_开发说明_v0.3.md)。

## 实测能支持哪些判断

小方本次完成需求分析、目录、策略、创意铺排、完整文稿、风格确认、逐页图片提示词七阶段。完整文稿为21,326字符。操作方通过自然语言要求23页，实际创建29个不同页面任务，3页成功、26页积分不足。成功页为封面、目录、章节页，三个核心KV、真实改稿及可编辑交付尚未验证。

它已展示连续产出可读文稿、按任务裁剪目录、详细描述画面与统一提案包装的能力。实际策略及终稿也出现年份和统计对象口径漂移、模板词残留。上述问题可用于工作台的针对性验收，不能扩大为小方所有任务都存在相同问题。

工作台已经有历史梦之蓝26页可编辑PPT、图文一体海报及结构化自动排版样本，不能写成从未完成过视觉或PPT。当前通用产品的完整内容、排版、编辑和导出整链验收仍未完成。合成提供方工程验收、真实模型样本、用户审美认可与通用产品运行分开判断。

基线材料为[小方实测与对比](../../output/research/xiaofang-2026-11-03/m6-spring/运行观察与工作台对比.md)、[自动排版首版验收](../workflows/自动排版首版验收.md)和[当前开发检查点](../../.scratch/end-to-end-local-20261102/CHECKPOINT.md)。检查点会继续更新，这里不把其文档状态当作实时进程观察。

## 当前节点先完成，后续优化不插队

当前节点依照其已有范围和验收要求继续。本轮不把“证据优势”“改稿优势”或“小方对比胜出”新增为当前节点的放行条件，不为验证建议重开正在执行的项目。

当前节点结束后，先回读实际交付、遗留阻断和独立验收记录，再决定下一轮。若当前节点被阻断，沿现有恢复和问题处理机制推进；不能用“未来优化”标签绕过当前已有的阻断，也不能自行宣布该节点完成。

工程闭环验收检查状态、版本、预算、交接与成品关联是否正确。真实品质验收检查实际模型生成的事实、策略、文案和图片是否满足任务。前者通过不自动代表后者通过。下一轮只针对仍未被证据覆盖的缺口开展验证，避免重复建设。

## 优化建议与可行性

以下为静态兼容性判断。模块和接口存在说明有复用落点，不代表建议已经通过实际运行验证。

| 编号及顺序 | 建议与复用落点 | 对流程的影响 | 后续可验证结果 |
|---|---|---|---|
| 01，优先 | 核验结论进入策略、文案、完整文稿和页面后继续保留日期、对象、范围与缺口。复用来源核验、充分性、稿件引用与内容来源定位。 | 强化原有跨阶段交接；不新增主阶段。是否需要更改数据合同须在实施前核对。 | 已知错例能被发现并定位；正确引文不被误伤；后续改写不把假设升级成事实。 |
| 02，优先 | 统一展示计划任务数、实际任务数、已完成核心成果、未完成项和可用费用信息。先核对现有预算约束，再补展示或必要预留。 | 主要影响总览、任务与交付状态；若增加预算预留算法会影响派发，另行设计。 | 用竞品的3页成功、26页积分不足作状态展示示例，按本工作台实际任务与成果粒度验证部分完成；未知费用明确未知；已成功任务不重复消耗。 |
| 03，有条件优先 | 在既定额度与门禁内，优先争取展示三个核心方向，随后展开整套提案包装；额度不足时明确未完成项。 | 现有视觉先于正式排版，本就支持该业务顺序。先检查已有队列，缺口可能只在方向间调度和预览；不能直接重排当前队列或跳过评审。 | 限额时仍能评估核心创意；不把封面、目录当三案完成。若现有顺序已满足则只做验收。 |
| 04，随后 | 验证三方向的依据、可见主张和画面机制是否有实质差异；落实匿名文案首读与产品资产检查。 | 验证既有策略、文案与视觉规则；不修改方向分类、数量或评分准入。 | 三案的有效区别能从实际文案与图像看出。共同品牌主题允许保留，不强制三套互斥策略或购买理由。 |
| 05，随后 | 用同一明确指令验证定向改稿，复用反馈、修订父稿关系、逐项落实检查和历史版本。 | 文字部分已有执行基础；视觉与跨页影响范围需补验证，可能涉及新接线。 | 修改未涉及共同上游或共享内容时，只改方向二，一、三和事实引用保持；涉及共享内容则说明影响并复核关联成果；旧稿和意见可回看。 |
| 06，后置扩充 | 复用已认可样章和排版器，明确整案字体、网格、图像组织及结论页的变化规则，再按需要补页型。 | 改善排版阶段，不替换现有认可版式，也不强迫所有KV采用提案包装配色。 | 实际页面层次清楚、跨页统一；原生文字和图示可编辑、KV独立可替换；文件回读与实际编辑分别核验。 |
| 07，轻量补充 | 在任务卡确认后和各阶段成果前，提供可读概要、当前缺口与下一步。 | 改善现有总览和工作区展示；不增加必须确认的节点，不让WorkBot代替用户决定。 | 用户能说明当前核心问题、方案依据、进行中工作和需要自己决定的事项。 |
| 08，证据充分后讨论 | 评估各项评审的有效发现、误判、耗时和成本，再讨论投入。 | 可能改变评审编排、运行合同和准入，属于单独产品决定。当前保持全部既定角色及有效门禁。 | 在同任务、可比投入下比较有效发现和误伤；未证明收益前不新增角色，也不因追求速度删掉独立评审。 |

01和04是质量优势的主要验证目标，02和03保证投入能形成可见成果，05验证改稿价值。06的“后置”仅指扩充模板，不是延后当前节点已经要求的排版交付。07可在后续合适的小任务中处理。以上是讨论顺序，不含工期承诺。

静态落点已核读[后端能力说明](../../tools/workbench/README.md)、[内容来源定位](../../tools/workbench/content-source-locations.mjs)、[排版状态合同](../../tools/workbench/layout-status-contract.mjs)、[人工反馈与落实检查](../../tools/workbench/human-feedback.mjs)。其中来源定位覆盖其特定合同，不能据此宣称所有普通文稿都已支持统一来源定位。资源字节上限也不能当作货币或积分预算。

## 小方阶段交互的补充分析

本次实际记录有六次阶段暂停确认，依次位于需求分析、目录、策略主题推导、创意铺排、完整文稿和风格设置之后。第七阶段逐页图片提示词没有新的interrupt。公开Skill要求每轮展示阶段结果、等待用户反馈，并提供编辑与继续入口。本次经用户授权由操作方代做选择，记录不能当作六轮普通用户可用性测试，也没有验证实际改写后的交互质量。

这套交互将阶段产物和继续执行权交给用户，推导工作仍由系统承担。接口还返回部分公开推导和工具事件，但不能据此推断官网逐字展示全部返回字段，或用户必须逐步审批每一次搜索和推理。实际选择与回包见[运行记录](../../.scratch/m6-spring-pitch/decisions.tsv)及其对应calls目录。

| 可借鉴的行为 | 对工作台的后续建议 | 与现有流程的关系 |
|---|---|---|
| 每完成一个阶段先展示可读产物 | 先给核心结论、变化、缺口，再按需展开全文与证据；不让用户只看执行日志。 | 扩充建议07的总览和阶段展示，不增加业务阶段。 |
| 允许在阶段边界改方向或补充要求 | 意见绑定当前阶段、方向与版本，说明修改会影响哪些后续成果。 | 复用已有反馈、版本和失效机制；视觉影响范围仍需验证。 |
| 停在明确位置等待选择 | 到已配置的人工节点，说明正在确认什么、继续会做什么以及可能的投入。 | 沿用自动与辅助模式，不照搬小方六次强制确认。 |
| 展示推导过程的可读内容 | 展示依据、关键推论、备选、推荐理由和未验证假设；详细资料按需展开。 | 利用已有来源与策略，不要求用户阅读全部公开推导，更不把阅读或确认当事实核验。 |
| 完整文稿和风格设置之后再出整套页面 | 保留可审阅和修改的中间成果，减少最终文件才暴露错误的机会。 | 现有内容审查与排版依赖已经覆盖；无需因此新建确认阶段。 |

本次前四阶段的通用按钮标签均为“编辑计划”和“开始研究”，即使已经处在策略或创意阶段也沿用。工作台可以按上下文写清操作含义，例如“按此范围调研”或“采用此主题进入视觉”，同时区分“允许继续”“人工指定采用”和“核验通过”，不以一个笼统确认覆盖三种含义。

自动模式在既有授权、预算和门禁内继续执行，阶段结果可查看、可提出修改；进入辅助模式勾选的节点时才等待明确决定。异常、额外付款和重大方向变更依原规则处理。该补充仍为待讨论建议，未制作交互样机或开展可用性测试；前述独立静态核查报告对应原八项建议，不作为本新增交互部分的独立验证。

## 工作台交互实现盘点与待补清单

2026年11月3日补充。此次核查读取当前仓库源码与既有验收记录，不访问现场服务、浏览器、进程或数据库，也不运行测试和模型。因此“已接”表示当前代码能追到实际HTTP请求或后端处理，不表示当前运行版本和浏览器交互已通过本轮验收。

## 验证方法与边界

本轮按poteto-mode的Investigation方法做只读可行性核查，并按technical-writing整理文档。核查内容为现行规则、实现落点、改动影响和建议是否重复已有能力。独立静态核查已完成，结论为八项建议有兼容落点，其中调度、预算算法、视觉跨页修订和评审编排需条件验证或产品决定。主文已收紧额度保证、竞品任务粒度及局部修改边界三处表述。独立核查记录保存在[流程兼容性与可行性核查](../../.scratch/xiaofang-followup-20261103/feasibility-review.md)。

本轮不运行真实模型或付费图像任务，不修改当前冻结合同，不操作运行中数据库、服务或任务。独立核查最多支持“静态可行”“需条件验证”或“需产品决定”，不支持“优化效果已验证”。

交互实现补充另经前端、后端只读盘点及综合核查，按原版用户面、旧操作页、合成工程入口与待运行验证分开记录。已发现的接线与展示缺口仅列入后续清单；本轮未进行浏览器实测，不把历史联调范围覆盖到当前源码明确未接的命令。

下一轮实施前，按实际选定的建议核对接口和冻结协议，拆成可验收的小单元，再运行必要的隔离检查及真实成品验证。运行中合同不热改，历史原稿、评分和失败回执保留。原流程中的用户授权要求继续生效。

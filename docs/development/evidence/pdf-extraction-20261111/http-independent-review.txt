## [P2] retry提交后缺少实际claim时的卡/修订守卫

位置：tools/workbench/brief-intake-service.mjs:143–144；关联intake-runtime.mjs:122–130。

fresh retry_local先核当前卡和请求修订，再await intake.humanAction登记queued；随后调用不带localRequest的intake.execute。document类runtime不会执行intakeCurrent卡检查，send又读取最新revision，因此两步间的合法换卡不会阻止新attempt。相同初次extract路径有localRequest守卫，而这条新retry路径没有。

独立可复跑证据：brief-extraction-independent-retry-race.mjs。仅新临时SQLite，先登记一个本地failed attempt；在真实intake-retry-local提交后，用store wrapper确定性插入真实revise-task-card命令，再让产品代码继续。此注入用于排定并发写入先后，不改产品代码或数据库字节。实际Python结果：

```json
{"result":"reproduced","claims":[{"active":"next-card","kind":"intake-start"}],"isCurrent":false,"status":"partial","attempts":2}
```

即实际新claim发生时active已是next-card，但旧原件仍被解析。可由其他进程对同一明确数据库的合法编辑造成。应在实际start时对当前卡及预期revision做与初次extract同强度的校验；retry ledger已登记可以保留为queued待核，不能因为登记成功而越过换卡。

同一问题也影响已commit queued retry的重放分支（brief-intake-service.mjs:130–131）：cap await后的revision检查与execute内真正start之间，runtime仍按新读head发送。独立脚本brief-extraction-independent-queued-retry-race.mjs保留原retry ledger，使用read wrapper在runtime execute首次读取时确定性排定另一写入；不伪造存储字节或原request。真实Python输出：

```json
{"result":"queued-replay-reproduced","claims":[{"active":"next-card","kind":"intake-start"}],"isCurrent":false,"status":"partial","attempts":2}
```

fresh retry与queued恢复应共同修复实际claim守卫，不能只在service层提前检查。

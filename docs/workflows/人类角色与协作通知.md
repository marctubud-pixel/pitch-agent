# 人类角色、在线状态与自动完成通知

2026-11-08，依据用户明确说明记录；用户随后授权直接实施。本轮前端已实现本地成员在线、角色权限、意见追溯及负责人站内收件箱，详见[实际实现与边界](../../.scratch/frontend-ui-optimization-20261108/source/proposal-workbench/docs/TEAM-COLLABORATION.md)。真实账号、跨设备同步、夜间后台与外部消息尚未接入，不恢复暂缓的业务流程。

## 已明确的人类角色

项目以比稿负责人这一人类角色为中心。用户另列出工作台使用者、人类视觉负责人、设计师，以及游客。上述角色不再按“一位人类使用者加多个智能体”概括。

| 角色 | 本轮明确的范围 |
| --- | --- |
| 比稿负责人 | 人类核心角色；自动模式完成方案后的通知对象。 |
| 工作台使用者 | 用户单独列明的人类角色，详细职责及与其他角色的关系待定。 |
| 人类视觉负责人 | 用户明确要求存在的真人角色，须与视觉智能体岗位区分。 |
| 设计师 | 用户明确要求存在的真人角色，具体操作及审批范围待定。 |
| 游客 | 可以查看，没有任何编辑权限或交流权限。 |

下表保留最初需求；本轮实施采用的默认细分权限见实现说明，已在界面权限说明和服务包装一致执行。游客禁止编辑及交流；下载和对外分享能力不在本轮新增范围。

## 在线状态

界面右上角需要明确显示人类成员谁在线，用户以飞书文档的在线成员感受作为交互参照。此处的人类在线信息与智能体岗位、任务运行和交接状态分别呈现。

当前采用右上角姓名/角色及人数，点击展开成员。在线按项目和同一站点的实际浏览器窗口统计，隐藏窗口显示离开，心跳超时离线。各名字标注示例成员，不能视为真实跨设备同步。

## 自动模式与完成通知

用户希望自动模式可在夜间自行运行，到第二天早上完整跑完方案，并在方案完成后自动发消息或艾特比稿负责人，使其能够看到结果。

这是完成触发的通知目标。用户没有在本轮确定通知渠道、具体收件账号、固定发送时间、截止时刻、已读规则或通知重发方式；本轮不创建自动任务，不发消息，不接入付费或真实业务运行。

“完整跑完”的完成条件仍需与既有生产、独立评审和交付条件对齐，不能将启动成功、阶段完成、失败或受阻包装成整案完成。失败或需要人工决定时是否通知及如何呈现，属于后续待讨论事项。

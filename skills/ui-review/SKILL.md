# UI审核

保留产品任务、数据含义、品牌约束和现有可用交互。通过实际界面定位问题，直接实施当前授权范围内的修改，并提供可追溯的前后证据。

## 1. 建立基线

读取项目说明、启动方式、已有组件和设计变量。确认目标页面、用户任务、目标设备和允许修改的范围。从项目和界面可观察的信息中推断；只有无法推断且影响实施的产品选择才询问用户。

按可用输入决定执行能力：

| 输入 | 立即执行 | 完成声明的上限 |
| --- | --- | --- |
| 可运行项目或获准编辑的应用 | 启动、操作、记录基线，修改并复验 | 实际观察到的页面、设备与状态 |
| 源码但无法启动 | 修改可确定的问题，记录启动障碍和静态证据 | 已修改，运行效果未验证 |
| 只有截图 | 标注位置、问题、建议与验证计划 | 视觉诊断；交互、精确颜色和实现效果未验证 |
| 只有网址且没有编辑入口 | 读取或操作可访问页面，提出有位置依据的改动 | 已检查；实现需编辑入口 |

能力不足时继续完成可做部分。需要实际源码或权限才能修改时，明确缺少什么。截图不等于编辑入口，也不证明响应式和交互可用。

在修改前保存目标页面截图、运行入口、视口、缩放、主题、语言、数据及状态。固定动态数据和动画的方式要记录。已有测试结果可记录为基线，不能冒充本次运行结果。

项目已有独立经验记录时，只查与当前任务有关的条目，将其作为待核对的案例证据；既有规则和当前任务约束仍是执行依据。

完成条件：能描述主要用户任务，且有可复现基线或明确的能力限制。

## 2. 判断问题与适用原则

先核对每项拟修改所依赖的可见事实，再选择原则。涉及图组身份或顺序、遮挡或缺失、跨页位置差异、数字测量时，读取并执行 [视觉事实核对](references/visual-evidence.md)。核对不能支持的判断保留为待确认，不据此实施语义性重排。

读取 [20 条原则](references/principles.md)，逐项标记：

- `需修复`：有可定位问题，并能解释它对用户任务的影响。
- `已满足`：实际检查后有证据支持保留。
- `不适用`：对应场景不存在，写出原因。
- `无法验证`：输入或工具不足，写出缺失证据。

一条原则可对应多个发现。一个发现也可关联多条原则。未看到的状态属于无法验证，不属于已满足。

为每项拟修改问题记录：页面位置、观察证据、受影响任务、原则编号、预期改善、验证方法。优先处理不可读、误导状态、不可操作和内容丢失，再处理层级、分组和装饰。只有审美偏好而无任务收益时保留现状。

完成条件：20 项有处置状态；每个拟修改问题有可验证预期，且关键事实能回到原材料核查。

## 3. 实施修改

沿用组件、设计变量和平台模式。先修主要内容与操作的层级、分组和宽度，再调整文字、色彩和相关细节。具体问题可以用最小的局部改动解决时，直接局部修复。

灰度、弱化、留白和彩边等都是按条件选用的方法，不是统一风格。保留专业指标标签、必要边界、既有品牌特征、语义和可访问名称。针对高密度工作台，先明确分组，保持用户需要的信息密度。

在代码或当前应用中直接完成已授权修改。修改共享组件或变量时，检查其相关使用位置，选择受影响的代表页面复验。保持路由、数据、表单提交、快捷键、权限和破坏性操作的既有语义；发现本来就有的缺陷时单独标注，避免冒充本次回归或擅自扩展任务。

完成条件：改动可查看；每项改动都能对应第二步记录的问题。

## 4. 按 Prove It Works 复验

读取 [验证方法](references/verification.md)。在同入口、同数据、同主题和同视口下重新打开修改后的真实界面。等待页面内容和字体稳定。确认加载的是当前改动；保留一个能定位到实际运行内容的证据，例如当前资源内容或与修改直接对应的 DOM 和计算样式。

对每项问题执行预先选定的检查，再检查与改动相关的交互及状态。响应式项目至少覆盖目标桌面和窄屏；若项目只面向一种设备，记录原因并测试该设备的边界。用项目已有验证工具，或编写项目专用、可重复执行的检查。截图和自动检查共同支持结论。

出现回归就修复或撤销造成回归的改动，然后复验。若连续两轮未改善同一问题，停止重复微调，重新检查原因、观察方法和约束。遇到必须由用户决定的取舍，交付当前证据及具体选择。

完成条件：每项改动的检查有结果，相关功能无新发现的未处理回归。缺失证据明确标记，不能折算成通过。

## 5. 交付

简要说明改善了哪些用户可见问题，链接实际修改文件和前后截图。交付原则处置表、运行检查的命令与结果，以及未覆盖范围。适用时保存这些材料为项目内的一份报告。

将位置、事实、推断、修改条件及未验证限制完整写在主报告。20 项流程处置可放附录，只引用主报告中的发现；附录不承载独有的实质判断或限制。用户指定交付结构时沿用该结构。

将结论限定为“已修复并验证”“已修改但未运行验证”“仅提出建议”或“仍未解决”。若检查后无需修改，保留界面并给出证据。避免把规则覆盖数、编译成功或模型自评分当作设计有效性的证明。

## 6. 简短复盘与有条件修订

每次使用结束，通常用1至3句说明哪些判断得到证实或推翻、哪些效果仍未验证；没有新证据时保留当前规则。出现可核实的新经验或维护候选时，再读取 [使用后复盘](references/learning.md)。经验与项目偏好单独保存，不直接追加到本文件。

重复或严重且可复现的问题才进入修订验证。优先合并、收窄或删除现有规则，能用检查方法解决的就改善检查。只有通过旧失败、新案例与保护案例的复验，并经独立 `gpt-6.1-sol` 复核，才更新已获维护授权的版本；证据不足时保留候选与当前版，不中断本次界面任务。

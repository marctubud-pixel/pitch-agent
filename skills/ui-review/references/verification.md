# 验证已有界面优化

遵循 Poteto 的 Prove It Works：检查实际运行的当前产物，既检查结果，也检查得到结果的过程。这里把它变成界面优化可复用的证据要求。执行不依赖 Poteto 插件，也不要求安装特定浏览器工具。

## 先定义检查对象

若发现依赖图组语义、缺失或遮挡、数字测量，先按 [视觉事实核对](visual-evidence.md) 回到原材料确认。检查规则是否被引用不等于关键事实成立。

为本轮维护一份简短报告。每个发现使用下列记录，格式可用 Markdown 表格或项目已有结构：

| 字段 | 含义 |
| --- | --- |
| 位置与任务 | 路由、组件和用户要完成的事 |
| 基线证据 | 截图、实测值或可复现交互 |
| 原则编号与处置 | 需修复、已满足、不适用、无法验证 |
| 预计变化 | 用户可观察的改善，修改前填写 |
| 保护项 | 本轮需保留的语义、操作和信息 |
| 复验方式 | 入口、设备、状态、操作和判断依据 |
| 实际结果 | 通过、失败或未验证，并链接原始证据 |

无需为无关原则生成冗长报告。20 项处置表可紧凑呈现；详细记录只覆盖实际发现。

## 建立可比较条件

前后使用同一路由、数据、视口、像素密度、缩放、主题和语言。等待字体及关键内容完成加载，记录稳定化方式。用当前 UI 或资源内容确认修改实际生效。截图文件时间和代码提交号本身不足以确认浏览器正在运行新版。

改变数据集、把长文案改短、换图片或隐藏困难内容后得到的截图，不能直接当作同条件改善证据。必要内容必须保留；明确授权的内容修改单独说明。

## 用合适证据检查结论

| 结论 | 检查方法 | 不能据此推断 |
| --- | --- | --- |
| 内容无横向溢出 | 测量滚动宽度和可见元素边界，再看截图；允许必要且可操作的数据表内滚动 | 隐藏 overflow 后内容仍完整 |
| 文字可读 | 测量实际前景、背景、字号与字重；复杂背景检查实际合成区域 | 浅色背景或某个类名自动达标 |
| 分组更清楚 | 同条件截图及相关组内、组间距离，说明用户读取关系 | 某个固定间距倍数普遍最佳 |
| 主要操作更突出 | 正常与灰度截图、任务路径检查 | 页面按钮数量少就更好 |
| 状态可识别 | 真实触发状态，观察可见文字、符号和语义 | 仅新增隐藏标签足够 |
| 功能无新回归 | 实际执行受影响任务与相关已有测试，核对数据结果 | 编译成功等于交互正确 |
| 素材清楚 | 以目标呈现尺寸和像素密度查看 | SVG 永远适合任意尺寸 |
| 层级符合任务 | 人审截图，说明焦点与阅读顺序，并结合操作 | 自动评分能证明所有用户更喜欢 |

自动化能运行时保留命令、工具依赖、返回码和原始输出。检查失败应包含实际值与预期差异。缺少依赖、空结果、页面未加载和脚本异常属于验证障碍，不能被解释为设计问题，也不能算通过。

对重要的新检查先在原界面运行，确认能发现所预期的问题；再对修改后界面运行。只因程序抛异常而失败，不能证明检查有效。若界面原本没有某项问题，原始版本通过该项是正常的。

## 复验边界和交互

选取修改所影响的路径，而不是每次无差别跑全站。共享组件或变量影响面较大时扩大代表页面覆盖。

- 在目标设备与布局断点边界检查，使用真实长内容。Web 响应式页面通常覆盖桌面与窄屏；原生固定设备按项目范围处理。
- 在相关表单中检查标签、校验、提交、取消、键盘顺序、焦点可见性和错误恢复。
- 状态相关修改应检查正常、首次空态、筛选无结果、加载、失败以及对应恢复操作，按项目实际支持的状态选择。
- 改到文字或布局时，检查目标字体、内容语言及适用的放大条件。改到主题和边界时，检查受支持的深色或高对比度模式。

仅截图输入时执行能做的视觉检查，把上述动态检查列为未验证。仅源码输入且运行失败时保留静态修改证据，不生成冒充运行结果的效果图。

## 完成与停止

每项拟修复问题都有实际检查结果，相关回归已处理，或明确列出未完成项后，才结束本轮。两个连续尝试不能改善同一问题时重新诊断，避免无限调参。

“已验证改善”要求同时具备基线问题、可查看的改动和对同一问题的复验。20 项处置完整只证明流程覆盖。若没有任何需修改问题，完成检查并保留现状即可。

本 Skill 不提供审美或完整无障碍合规的绝对保证。它提供逐项可审查、可复现、允许失败的证据链。对真实用户效率的结论需要代表性任务和用户研究；对 Skill 相比默认模型是否更好的结论需要有对照的独立评估。
